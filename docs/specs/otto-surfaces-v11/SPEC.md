## What this spec is, and is not

This is H1.4 and the H2.1/H2.2/H2.4 slice that H1.4 unlocks, written down as checkpoints a suite
can prove — nothing more. It does not re-plan the roadmap, does not move a horizon date, and does
not add a platform layer. Every checkpoint below rides the five planes v1 (crew#768) already
builds — gateway, verification, memory, router, observability — through the socket v1 is already
building (`otto/surface/`, `SurfaceAdapter` Protocol, capability negotiation, the `ambient` trust
class, the no-voiceprint rule). Voice and vision are adapters plus capability flags on that
socket, exactly as the day-0 contract promises: "zero gateway change."

## Provider agnosticism (LAW 19, LAW 34) — no vendor named in core

Transcription, synthesis and vision description sit behind capability interfaces the same way
the router already treats model providers as swappable lanes:

- `otto.voice.Transcriber` — `transcribe(audio: bytes, mime: str) -> TranscriptResult`. Provider
  selected by `OTTO_STT_PROVIDER` (env, never a literal in code). No STT vendor is named in
  `otto/voice/` core; the provider adapter is a leaf module, swapped by config.
- `otto.voice.Synthesizer` — `synthesize(text: str, voice_profile: str) -> AudioResult`. Provider
  selected by `OTTO_TTS_PROVIDER`. Same rule.
- `otto.vision.Describer` — `describe(image: bytes, mime: str) -> DescriptionResult` with
  provenance (source surface, task ULID, timestamp). Provider selected by `OTTO_VISION_PROVIDER`.
  The describer is a router lane like any other model call — it rides the router's existing
  budget guard and cost-by-lane metric, not a new call path.
- Every one of the three interfaces is a Protocol in `otto/voice/` and `otto/vision/`; a fake
  double satisfies it for every BDD scenario below, so the suite proves the contract, never one
  vendor's API.

DSPy (R64) governs every prompt these three interfaces' default adapters use — the vision
describer's captioning prompt and the voice pipeline's any text-shaping prompt are DSPy modules,
compiled and evaluated the same way the router's own prompts are, never a hand-written string in
application code.

## 1. Channel plane — the adapter registry, concrete (extends SURFACE-CONTRACT-DAY0.md)

The day-0 contract (crew#768) defines the `SurfaceAdapter` Protocol and the envelope shape. This
spec makes it a *registry*: adapters register their capability set at boot, the gateway holds one
map (`surface_id -> capabilities`), and negotiation is a lookup, not a per-request guess.

- **Registry**: `otto.surface.registry.register(adapter: SurfaceAdapter) -> None`, called once per
  adapter at process start; `otto.surface.registry.capabilities_for(surface_id) -> CapabilitySet`
  is the single source the router's `render()` hook consults. A surface that never registers
  cannot receive a rendered response — fails closed, not a silent text-only default.
- **Capability negotiation, formalized**: `CapabilitySet` is a frozen set of
  `{text, rich, voice_in, voice_out, image_in, image_out, approval_gesture}` — the same vocabulary
  the day-0 contract already names. Negotiation is: the router asks the registry what the
  responding surface can carry, and renders down to the richest form that surface supports. A
  degrade is always an explicit line in the rendered message (day-0's rule, inherited, not
  redone).
- **Per-surface rendering**: `render(response, capabilities) -> RenderedMessage` gains one more
  hard case: when the response itself required voice or image, the renderer states what would
  have been produced ("voice reply available as text — this surface has no `voice_out`"), never
  silently drops the modality.
- **Session and thread continuity**: every inbound envelope carries `principal` (identity plane,
  day-0) and gains `thread_id`. The presence store (section 4) keys on `principal`, not `surface`
  — a thread is portable across surfaces by construction, because the key that finds it was never
  the surface to begin with.

## 2. Voice in — transcription, riding the adapter contract

- Inbound audio (Telegram voice note is the first binding — Telegram already carries `voice`
  messages, no new bot capability needed) reaches the Telegram adapter, which calls
  `otto.voice.Transcriber.transcribe()` and normalises the result into the SAME task envelope as
  a text message: `envelope.content = transcript.text`, `envelope.modality_in = "voice"`,
  `envelope.transcript_confidence = transcript.confidence`. The gateway, tiers and taint rules see
  a task envelope exactly as they do for text — the day-0 promise ("zero gateway change") holds
  because voice never introduces a second code path into the gateway.
- **Trust class of a transcript**: a voice note from the founder's bound Telegram account is
  `operator` — identical to a typed message from the same account. Trust comes from the
  *principal binding of the surface*, never from the audio itself (this is the no-voiceprint rule
  applied to input, see section 3.1 for the authentication half).
- A transcript below a configurable confidence floor (`OTTO_STT_MIN_CONFIDENCE`, default set in
  config, never hardcoded) is not silently trusted — the low-confidence path renders an
  UNVERIFIED-style marker back to the founder asking for confirmation before the transcript
  becomes a task, the same pattern the router already uses for ungrounded claims (P1, crossing
  modalities).

## 3. Voice out — synthesis, and the no-voiceprint rule

- Outbound synthesis is a `render()` capability: when the responding surface's `CapabilitySet`
  includes `voice_out`, the router may call `otto.voice.Synthesizer.synthesize()` on the final
  response text and attach the audio to the rendered message. Text always accompanies audio —
  voice output is an addition to the universal response contract, never a replacement for it, so
  every UNVERIFIED marker and every claim's evidence reference still exists in the text channel
  even when a voice channel also plays.

### 3.1 No-voiceprint rule — hard invariant

- **The rule**: voice is never an authentication factor, in either direction. `principal` is
  resolved solely from the surface's bound identity (Telegram account id, passkey-bound device on
  the future companion app) — never from anything in the audio stream, and never from a claim
  embedded in a transcript ("this is Chidi").
- **Enforced as validation, not convention**: `otto.identity.resolve_principal(envelope)` never
  reads `envelope.transcript` or any voice-derived field; a transcript containing an identity
  claim is inert data, same as any other untrusted text. This is the day-0 contract's rule
  (`SURFACE-CONTRACT-DAY0.md` item 4) exercised for the first time by a real voice binding —
  written once, tested now that there is a producer to test it against.
- **Adversarial case**: an attacker sends a voice note to the founder's bot channel claiming to be
  the founder, or plays a recording of the founder's voice. Both fail identically — the
  `principal` is resolved from the channel's own binding (whoever's Telegram account the message
  arrived on), so the content of the recording changes nothing about who the actor is deemed to
  be.

## 4. Vision — image_in day 0, `ambient` classification, Vision Stage 1 alignment

- **Telegram photos, day 0**: an inbound Telegram photo reaches the adapter, which calls
  `otto.vision.Describer.describe()` and attaches the result to the envelope as
  `envelope.image_description` with full provenance (`source_surface`, `task_ulid`, `captured_at`).
  The image bytes themselves are never forwarded into a tool call or a prompt beyond the
  describer — only the described text, carrying its trust class, moves further into the system.
- **Trust class: `ambient` by default**. An image arriving as an attachment to an operator's own
  message (the founder sends a photo directly, in his own Telegram thread) is `ambient` —
  observation, not instruction — exactly as the day-0 contract already states for camera/mic
  input generally: "observations, never instructions." An image is promoted to carry instruction
  weight only when the founder explicitly attaches it to a command in the same message
  (`operator`-attached), and that promotion is an explicit envelope field
  (`envelope.image_operator_attached: bool`), never inferred from the image content.
- **Taint cap, proved**: text printed inside an image (a sign, a screenshot, a QR code decoded to
  text) can describe anything it wants — the describer's output is still `ambient`-classed data,
  so it is capped at the gateway's existing taint rule (day-0 item 3, v1 CP2's taint-cap test)
  exactly like any other untrusted text block. This spec adds the printed-text-injection case to
  the existing red-team suite; it does not invent a new enforcement point.
- **Vision Stage 1 alignment (crew#770 H2.4)**: "images/frames as first-class task inputs; glasses
  capture → described observations with provenance into memory." This spec's `image_description`
  field with provenance is exactly that shape — H2.4's glasses-camera producer is a second
  `image_in` adapter registering against the same `Describer` interface and the same `ambient`
  classification; nothing here is rebuilt when glasses arrive, per the day-0 promise.

## 5. Conversational presence — one conversation, many surfaces (H2.2 v1.1 slice)

Full scope: "start a thread on glasses, continue at the desk, finish by voice in the kitchen —
one conversation state, per-surface rendering" (crew#770 H2.2). This spec builds the slice that
does not need glasses or the companion app to prove: a Telegram thread and a second surface
(minimal HTTP, the same binding the day-0 contract already proves with) sharing one state.

- **Presence store**: `otto.presence.Store` — a table keyed on `(principal, thread_id)`, holding
  the task/session references a conversation has accumulated, backed by the existing Postgres
  instance the memory plane (v1 CP4) already runs — no second database, the headline rule again.
- **Continuity contract**: a message on surface A referencing an open thread (explicit thread
  reference, or the adapter's own "reply" semantics where the surface has one, e.g. a Telegram
  reply-to) resolves to the SAME presence record a message on surface B would resolve to, if both
  carry the same `principal` and `thread_id`. The router's context assembly (v1 CP4) reads from
  the presence record before it reads from surface-local history, so continuation never depends
  on which surface holds the message log.
- **Per-surface rendering stays surface-local**: the SAME conversation renders differently per
  surface (rich cards on one, plain text on another) — presence unifies *state*, never *shape*.
  This is the day-0 renderer's job, unchanged; presence only feeds it the right prior turns.
- **Scope boundary, explicit**: this checkpoint does NOT build the companion app (H1.2), does NOT
  build the glasses surface (H1.3), and does NOT build push notifications for a mobile app — those
  remain their own horizons. It proves the presence *kernel* — the store and the continuity
  contract — against the two surfaces that already exist by day 0 (Telegram, minimal HTTP).

## 6. Observability — every envelope, every surface, one ULID (LAW 50)

- Every voice, vision and cross-surface envelope carries the SAME task ULID the spine already
  mints (v1 CP1) — transcription, synthesis and description calls are router-lane calls, so they
  inherit `otto/obs`'s `instrument()` wrapper and ULID propagation with zero new instrumentation
  code (v1's `OBSERVABILITY-DEMO-ONBOARDING.md` W1/W2, reused, not re-opened).
- **`otto-obs-coverage` gate, component list extended**: the gate's component list is generated
  from the signed capability inventory (never hand-kept, per v1's rule) — this spec's inventory
  entries (`otto/voice`, `otto/vision`, `otto/presence`) are picked up by the same generator, so
  the gate refuses launch if a voice, vision or presence span is absent from the backend, exactly
  as it already refuses for spine/gateway/verify/memory/router/obs.
- **No black box across modalities**: a task that started as a voice note and finished as a
  rendered card is reconstructable end to end from its ULID alone — trace search (SigNoz), model
  calls including the transcription/synthesis/description calls (Langfuse), decisions
  (`otto replay`), verdicts (signed ledger). One id, four mirrors, voice and vision included.

## Build order and parallelization

CP order is the build order. CP1 lands first — it is the only checkpoint every other one calls
into. CP2, CP3, CP4 and CP5 then run as four fully parallel lanes: each owns a new, disjoint
directory, registers itself against CP1's registry API, and never edits a file another lane owns.
CP6 depends on CP2–CP5 emitting spans (each of their own lanes calls `otto/obs`'s `instrument()`
directly, so CP6 adds nothing to their files) and on the capability inventory being generated,
never hand-kept, so no lane hand-edits a shared list. CP7 is the verification lane — new test
files only, run once CP2–CP6 exist to attack.

Lanes start when the v1 integration wave (crew#768) completes and frees machine headroom; v1
launch stays the critical path. No lane in this spec touches the v1 checkpoints' files.

**Hardware-coupled items stay out of this spec's scope, by design** (section 5's scope boundary):
the companion app (H1.2, app-store presence) and the glasses surface (H1.3, device pairing) are
not checkpoints here — CP1–CP7 build software interfaces only (Telegram and minimal HTTP), so no
checkpoint below needs a `FOUNDER ACTION` for a device or a store listing. When H1.2/H1.3 are
picked up as their own spec, their checkpoints name the device-side founder action explicitly at
the point they need it — inventing one here, with nothing to act on yet, would be a false blocker.

## Checkpoints

Each checkpoint's Definition of Done is the exact command a suite runs, not a description.
Verified by `@pytest.mark.cp1` … `@pytest.mark.cp7` in `checkpoints/` — scoped to this issue;
title text disambiguates from v1's CP1–CP7 (crew#768) wherever both appear in the same view.

### CP1 — Channel plane: adapter registry and capability negotiation
**Owns:** `otto/surface/registry.py, otto/surface/negotiate.py, otto/surface/render_degrade.py` — see the Build order table for what it reads and what runs in parallel.
- `otto surface list-adapters` shows Telegram and the minimal HTTP surface each registered with a
  distinct, non-empty `CapabilitySet`; exit 0.
- `otto test render-degrade --surface telegram --response voice_out` shows a voice-only response
  rendered as text on a surface without `voice_out`, with an explicit degradation line in the
  rendered message body — never a silently dropped modality.
- `otto test envelope-parity --surface telegram --surface http` sends identical content through
  both adapters and diffs the two resulting task envelopes: zero diff outside `surface` and
  `principal` fields (day-0's own acceptance test, re-run here as this spec's regression floor).
- Edge case: an adapter that fails to register at boot cannot receive a rendered response —
  `otto test render --surface unregistered` returns a named failure, never a default text
  fallback.

### CP2 — Voice in: transcription pipeline, Telegram voice notes as first binding
**Owns:** `otto/voice/transcribe.py, otto/voice/stt_provider.py, otto/tests/cp2voice_in/` — see the Build order table for what it reads and what runs in parallel.
- `otto test voice-in --fixture telegram-voice-note` shows a Telegram voice message produces a
  task envelope with `modality_in: voice` and a transcript matching the fixture's known text;
  exit 0.
- `otto test voice-in --fixture low-confidence` shows a transcript below
  `OTTO_STT_MIN_CONFIDENCE` renders a confirmation request instead of proceeding as a task
  directly.
- Network/bandwidth edge case: the transcription provider times out — the task fails closed with
  a named `TRANSCRIPTION_UNAVAILABLE` state, never silently treated as an empty message.

### CP3 — Voice out: synthesis pipeline and the no-voiceprint rule
**Owns:** `otto/voice/synthesize.py, otto/voice/tts_provider.py, otto/identity/no_voiceprint.py, otto/tests/cp3voice_out/` — see the Build order table for what it reads and what runs in parallel.
- `otto test voice-out --surface telegram-voice-capable` shows a rendered response includes both
  the text and a synthesized audio attachment when the surface's `CapabilitySet` includes
  `voice_out`.
- `otto test voiceprint-auth --scenario audio-identity-claim` shows a transcript containing "this
  is Chidi" from a non-founder-bound channel resolves `principal` from the channel binding alone;
  the claimed identity in the transcript has zero effect — exit 0, principal unchanged.
- `otto test voiceprint-auth --scenario replayed-recording` shows a played recording of the
  founder's own voice, arriving on a channel not bound to the founder's account, is refused the
  same way — principal never derives from audio content.

### CP4 — Vision: image_in day 0, `ambient` classification
**Owns:** `otto/vision/describe.py, otto/vision/vision_provider.py, otto/tests/cp4vision/` — see the Build order table for what it reads and what runs in parallel.
- `otto test vision-in --fixture telegram-photo` shows a Telegram photo produces
  `envelope.image_description` with provenance (`source_surface`, `task_ulid`, `captured_at`) and

- `otto test vision-in --fixture operator-attached` shows a photo sent alongside an explicit

### CP5 — Conversational presence: cross-surface continuity
**Owns:** `otto/presence/store.py, otto/presence/continuity.py, otto/tests/cp5presence/` — see the Build order table for what it reads and what runs in parallel.

### CP6 — Observability: voice, vision and presence spans reach the collector
**Owns:** `otto/obs/components/voice.py, vision.py, presence.py, otto/tests/cp6obscoverage/` — see the Build order table for what it reads and what runs in parallel.

- `otto replay <task_id>` for a task that crossed voice-in, vision-in and a surface switch

### CP7 — Constitution extended: no-voiceprint and `ambient` hold under adversarial test
**Owns:** `otto/tests/redteam/voice_vision_canary/, otto/tests/cp7constitution_v11/` — see the Build order table for what it reads and what runs in parallel.
- `otto test key-isolation --process voice-pipeline` and `--process vision-pipeline` show neither
  process holds prover signing key material (P1, extended to the two new lanes).
- `otto redteam run --suite voice-vision-canary` runs the no-voiceprint and printed-text-injection
  canaries from CP3/CP4 as a standing, scheduled suite (not a one-off manual run) — zero leaks on

- `otto eval run --suite groundedness --modality voice,vision` shows the P3 groundedness rule

  carrying a vision description, not just text-originated tasks.
